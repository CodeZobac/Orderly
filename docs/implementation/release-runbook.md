# Orderly release and recovery runbook

Status: prepared, not executed. Release is blocked on authorized acceptance, verified Supabase GitHub deployment, real provider setup, recovery rehearsal and selection/authorization of a hosting environment. This runbook never authorizes production changes or test execution by itself.

## Release preparation

1. Review all phase handoffs and the migration diff. With explicit test authorization, run in source: `npm run lint`, `npm run typecheck`, `npm run build`, `npm test`, `npm run test:integrations`, `npm run test:github`, `npm run test:notion-setup`, `npm run test:billing`, `npm run test:browser`. Browser fixtures require exclusive Next dev-directory access and ports 3200/3001. Real parallel sessions require a multi-connection Postgres preview, not PGlite alone.
2. Validate server configuration with `npm run config:validate`. Store credentials only in deployment/ignored secret files, never NEXT_PUBLIC variables. The same database, integration encryption key and provider credentials must reach app and worker. Syntax validation does not verify credentials. Register exact HTTPS callback/webhook URLs per provider handoff. Complete Notion developer-portal verification; unsigned setup captures must be reviewed explicitly.
3. Verify Supabase dashboard GitHub integration for CodeZobac/Orderly: directory source, main production branch, source/supabase/migrations. Require preview success when branching/protection is enabled. Commit/push/PR and production changes require the user workflow authorization. Never use direct apply as a shortcut. After deployment, inspect migration history, private RLS/grants and security advisors with Supabase MCP. Verify the new RPC signatures and trigger guards in the preview before release.
4. Complete the real provider/task/timer/evidence/billing journey. Check two billable hours at 60 plus one non-billable hour gives 120, extra PRs do not change amounts, edits/provider renames do not alter finalized reports, adjacent periods cannot overlap, duplicate/multi-session finalize cannot double-bill, and void/reissue retains history. Check 23/25-hour DST days, unsupported currencies, ISO precision, formula-injection exports, long/running guards, stale drafts and ownership. Compare UI task/line/currency totals with CSV and printed saved snapshots.
5. Verify keyboard navigation, field labels, errors/retry, focus and reduced motion; 320/375/414/768/1440px views and print pagination/long URLs; measure all existing/new text/control pairs against the required contrast thresholds. New source styles alone are not evidence of acceptance.
6. Authorize/select hosting, configure HTTPS and supervised app/worker. Deploy a reviewed artifact (`npm run build`, `npm start`) after migrations. Do not run production smoke fixtures on real data: they create accounts/work. Stage/preview verification precedes traffic cutover. Record exact release commit, migration history, configuration version (names only), verification and recovery evidence before clearing the release candidate.

## Operations

- Deploy app and sync worker as separate supervised services. Worker entrypoint `npm run sync:worker`; SIGTERM/SIGINT lets it complete the current page. Three-minute leases expire after a crash; replay and event dedupe preserve durable work. Keep outbound provider access and shared encryption key available. Never run two incompatible worker versions during a schema change.
- Settings → Durable sync monitoring gives owned source/job state; an authenticated GET /api/operations offers the same no-store data. Examine stale successes (>1h), overdue eligible jobs (>1h), >=5 retry attempts, disconnected/reconnect/inaccessible sources and expired leases. Investigate supervisor/worker logs, reconnect/remap or resync in Settings. A last-success timestamp may reflect a page read, not an entire scan. Monitor worker process uptime externally; this UI is not an automated pager.
- Track application request failures, DB availability, queue lag, provider rate limits and backup success without logging provider tokens, webhook payloads, passwords or session cookies. Configure alert recipients/retention with the chosen host. Full-state scans, unpaginated billing history and audit growth need production query-plan/volume review; do not delete finalized snapshots/allocations/audit to reduce costs.
- Billing corrections: void every report allocating the entry, give an audit reason, edit/override after locks release, save/review/finalize a new draft. Export the replacement and explicitly withdraw historical copies. Only active finalized reports count; voided totals remain historical. No payments, tax invoice, conversion or provider writeback.

## Backup and restore rehearsal (only after authorization)

1. Choose encrypted off-site backup storage, retention, a recovery owner and required RPO/RTO. Verify the Supabase project's actual backup/PITR entitlement instead of assuming plan support. Keep a protected copy of ORDERLY_INTEGRATION_KEY and deployment configuration independent of DB backups; losing the encryption key makes stored provider credentials unreadable. A DB restore does not restore external callback registrations.
2. Pause app writes and stop workers for a coordinated snapshot and evidence capture. Use approved Postgres connection services/PGPASSFILE (0600) rather than inline password URLs. A full Orderly logical archive includes orderly_private tables/functions and public Orderly RPC functions, plus migration history. On a dedicated project, an example command is `PGSERVICE=orderly_backup pg_dump --format=custom --schema=orderly_private --schema=public --schema=supabase_migrations --no-owner --no-acl --file=/protected/orderly.dump`. Review exactly what public includes before adopting it; platform auth/storage backups are separate. Record migration revision, private table row counts, finalized snapshot hashes/exports and active allocation totals at this same pause boundary. Encrypt the archive and never commit it.
3. Restore ONLY into an empty isolated disposable Supabase/Postgres preview with matching extensions/platform roles. Disable external webhooks and keep the worker stopped. Example: `PGSERVICE=orderly_restore pg_restore --exit-on-error --single-transaction --no-owner --no-acl --dbname=postgres /protected/orderly.dump`. Full schema+data restore creates triggers after loading data; do not use an unreviewed data-only restore with live immutable-allocation guards. Use a compatible pg_dump/pg_restore major version. Restore integration secrets via the secret store. Reapply/review service-role-only grants and RLS from the exact migration version: --no-acl omits archive grants. An isolated generic Postgres requires anon/authenticated/service_role roles first. Never point this command at production.
4. With tests authorized, compare saved counts, interval/version/audit histories, finalized report JSON hashes and CSV amounts/evidence, allocation union and per-task active-timer uniqueness and account timer-capacity invariant. Verify independent login/session behavior, owned APIs, anon/authenticated denial, frozen report edits and replayed finalize/void requests. Prevent restored old sessions from gaining unintended public access; keep preview private. Revoke/re-authorize stale provider credentials before enabling outbound workers in a recovery. Test worker lease recovery only with isolated/mock sources. Record measured restore time and data loss against the chosen objectives.
5. Restore rehearsal is complete only with retained comparison evidence. No backup/restore was executed in Phase 4; no RPO/RTO has been demonstrated. Production recovery/cutover needs explicit authorization. Prefer rollback of the application to a compatible version plus a reviewed forward schema correction; never delete finalized billing history or force-reset migrations.
