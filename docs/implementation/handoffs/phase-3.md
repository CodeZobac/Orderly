# Phase 3 — GitHub App and work evidence handoff

Status: **implemented locally; acceptance verification and live activation pending** (2026-10-10). The user explicitly requested Phase 3 while Phase 2's live acceptance remains pending. No automatic progression to Phase 4.

## Delivered

- GitHub App user authorization with S256 PKCE and the current `2026-03-10` REST API version. Random callback state is hashed, ten-minute, single-use, bound to the initiating browser and independent Orderly session, and that session is rechecked at connection persistence. Installation callback IDs are never trusted as ownership proof. Independent Orderly sign-in remains unchanged.
- Server-only encrypted user/refresh tokens, serialized refresh through existing connection/job leases, RS256 App JWTs, and short-lived installation tokens restricted to one mapped repository and read-only metadata/pull-request permissions. App private keys remain in deployment secrets, not the database or UI. Each scan verifies current App installation state, user repository access and installation repository membership before reading PRs.
- Paginated installation/repository discovery, explicit repository → owned project mapping, and all-state PR imports through the existing worker. Stable repository/PR IDs, URL, title, author, head/base branches, state and canonical timestamps are retained. PR bodies are read transiently for matching, never persisted; no files, diffs or source code are fetched.
- Many-to-many canonical task/PR links. Exact Asana/Notion IDs or URLs in PR titles, descriptions or branches produce explainable suggestions; all suggestions require explicit confirmation, including single matches. No title/fuzzy matching. Confirmation, dismissal and unlinking are audited and idempotent; confirmed/rejected choices survive later imports. Unconfirmed suggestions are recomputed only from current metadata. Stale reads cannot regress metadata or revive old suggestions.
- Explicit canonical task selection before starting a timer from a PR. A standalone PR can create/reuse a local task with explicit billing-project assignment. Existing timer mutation APIs enforce one active timer, retry keys, owned attribution and explicit switching. Link changes never touch interval attribution, rates, duration or billing totals. Task pages show recorded history, source-task labels/status/URLs and linked PR evidence; PR panels show task-recorded totals labelled as task totals rather than PR-allocated hours.
- Signed raw-body GitHub webhooks, durable delivery dedupe before acknowledgement and queue enqueue, canonical-state reconciliation every fifteen minutes, manual reconciliation, durable cursors and retry/backoff/Retry-After. Revoked user authorization retires credentials/jobs; installation removal/suspension and repository removal fence in-flight jobs and mark evidence unavailable. Unsuspend/grant events only schedule a canonical access recheck, never restore access from an event body. Missing PRs become unavailable only after a complete successful scan. Historical tasks, PR metadata, links, audits and recorded time survive removal/disconnect.
- Today reminders for recorded tasks without confirmed PR links and imported PRs without confirmed tasks; optional links remain optional. The existing twelve-hour timer reminder stays advisory. Events never start/stop timers. Existing amber tokens and shared form/control styles are reused; layout wraps repository/branch text and controls on narrow screens.

## Architecture and API contracts

- CLI-generated `source/supabase/migrations/20261010104930_phase_three_github.sql`: adds GitHub to the existing connection provider constraint and creates private `pull_requests`, `pr_links`, `pr_events`, `pr_audit` with composite ownership FKs, RLS and service-role-only grants. No public/anon/authenticated data grants. RPCs use SECURITY INVOKER and an empty search path. A task with PR links/audit is retained when board relinking cleans up an otherwise unused auto-created task.
- Existing `connections`, `oauth_states`, `sources`, `sync_jobs`, `sync_events` remain the shared infrastructure. One GitHub connection per verified GitHub user; repository sources carry server-verified installation ID/name in mapping. A connection may span installations, with refresh serialized across them. Repository remapping changes import context, never existing task project or interval/rate attribution.
- `orderly_github(owner,command,input)` exposes owned snapshots, references, lease-aware mapping/recovery and audited linking. Server routes authenticate the opaque Orderly cookie, ignore client owner IDs, and require exact Origin for mutations. Snapshots exclude credentials and lease secrets; evidence availability also reflects current connection/source access.
- Existing `orderly_sync` is renamed `orderly_board_sync`, with a new wrapper retaining board behavior and implementing GitHub durable events/page persistence. GitHub page upserts and existing cursor/dirty-follow-up completion commit atomically. Owner → connection → source → job locks and generation/lease fencing prevent retired reads from writing evidence. `lib/integrations.ts` dispatches GitHub claims to `lib/github.ts`; `scripts/sync-worker.ts` continues to handle all providers. Next does not start a worker.
- `lib/github-provider.ts`: fixed API/token hosts, pinned version, JWT/PKCE, transient installation tokens, discovery, canonical PR normalization and exact matching. `lib/github.ts`: owned orchestration and one-page worker. Shared public types: `lib/github-types.ts`.
- `GET /api/github`: owned connection/source/PR/link/event/audit snapshot. `POST`: `install`, `installations`, `repositories`, `map`, `resync`, `disconnect`, `link`, `reject`, `unlink`, `local`. `POST /api/github/connect` starts authorization; `GET /api/github/callback` consumes browser/session-bound state; `POST /api/github/webhook` verifies raw HMAC and commits receipt/jobs before 204. The board API's list excludes GitHub connections/sources.
- `components/github.tsx`: Settings discovery/import/linking/timer UI, task evidence and Today reminders. `components/tracker.tsx` mounts these alongside existing tracker views; additive styles in `app/globals.css` use `tokens.css`.

## Setup and deployment

Run app commands in `source/`. Deploy all versioned migrations through the Supabase GitHub integration for `CodeZobac/Orderly`, working directory `source`, production branch `main`. Enable/verify the dashboard integration first and require the preview check when configured. No migration was applied directly and no remote deployment is claimed. The pre-existing Supabase deployment/access limits remain in [Supabase foundation](supabase-foundation.md).

1. Create a GitHub App. Repository permissions: **Metadata: read**, **Pull requests: read**. No contents, commits, issues or task/time write permissions are needed. Install on selected repositories. Subscribe to `pull_request`; GitHub also sends installation, installation-repository and authorization lifecycle events. Enable expiring user access tokens; Orderly requests `offline_access` and stores refresh tokens encrypted.
2. Configure the user authorization callback as `${ORDERLY_ORIGIN}/api/github/callback`. Orderly uses explicit user authorization; the installation flow is separate and does not bind an installation merely from a setup redirect. A setup URL may point to Settings if desired. Webhook URL: `${ORDERLY_ORIGIN}/api/github/webhook`, active with a strong webhook secret. Use an HTTPS tunnel for local development and register its exact stable origin/callback. The callback cookie is Secure/HttpOnly/Lax; the independent session cookie remains Strict.
3. Configure server-only values in ignored environment/deployment secrets: `SUPABASE_URL`, `SUPABASE_SECRET_KEY`, `ORDERLY_ORIGIN`, stable `ORDERLY_INTEGRATION_KEY`, `GITHUB_APP_ID`, `GITHUB_APP_SLUG`, `GITHUB_CLIENT_ID`, `GITHUB_CLIENT_SECRET`, `GITHUB_APP_PRIVATE_KEY` (RSA PEM; escaped newlines supported), `GITHUB_WEBHOOK_SECRET`. Never use a `NEXT_PUBLIC_` prefix. Share the encryption key, DB access and GitHub App credentials between app and worker; the webhook secret belongs on the app server. Blank examples are in `.env.example`.
4. Start `npm run dev` or `npm run build` then `npm start`. Start the separate persistent worker with `npm run sync:worker`; `npm run sync:worker -- --once` handles at most one due page across all providers. Supervisor restarts are recommended.
5. In Settings, install the App on selected repositories, authorize the GitHub account, choose an accessible installation, select/map a repository and owned billing project. Refresh evidence after the worker imports. Confirm exact suggestions or choose canonical Asana/Notion/local tasks explicitly; several links never multiply time. From a PR, choose a confirmed linked task before starting/switching the timer, or create a local task with explicit project assignment.
6. Recover access by restoring the installation/user permissions and reauthorizing if revoked, then remap or reconcile the repository. Stale negative lifecycle events conservatively mark unavailable; manual canonical reconciliation restores current access. Retained history is never deleted. After deployment, inspect migration history, private grants/RLS and Supabase advisors through MCP.
